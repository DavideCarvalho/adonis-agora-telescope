[`@adonisjs/otel`](https://docs.adonisjs.com/guides/digging-deeper/opentelemetry) traces your
app with OpenTelemetry and pushes the data to any OTLP backend. Telescope works with it in both
directions:

- **OpenTelemetry → Telescope.** Add `telescopeSpanProcessor()` to `config/otel.ts` and the
  spans OpenTelemetry records (pg, outgoing http, DNS, events, your own `@span()` methods) show
  up in the Telescope trace view, next to Telescope's own entries.
- **Telescope → your backend.** When `@adonisjs/otel` is running, Telescope sends its entries
  (exceptions, jobs, mails, diagnostics events…) through the destinations in `config/otel.ts`,
  in the same traces as the app's spans. You configure the endpoint and headers once, in
  `config/otel.ts`.

Without `@adonisjs/otel`, Telescope records and shows everything locally and sends nothing out.

## Install

Set up `@adonisjs/otel` first (it adds `otel.ts`, `config/otel.ts` and the provider):

```sh
node ace add @adonisjs/otel
```

`@adonisjs/otel` 2.x needs Node.js 22.15 or newer and OpenTelemetry JS SDK 3
(`@opentelemetry/api` 1.10). Telescope needs nothing more.

## Configure `config/otel.ts`

Add the processor to `spanProcessors`, and point `destinations` at your backend:

```ts title="config/otel.ts"
import { defineConfig, destinations } from '@adonisjs/otel'
import { telescopeSpanProcessor } from '@adonis-agora/telescope/otel'
import env from '#start/env'

export default defineConfig({
  serviceName: env.get('APP_NAME'),
  serviceVersion: env.get('APP_VERSION'),
  environment: env.get('APP_ENV'),

  // OpenTelemetry spans → the Telescope trace view
  spanProcessors: [telescopeSpanProcessor()],

  // Where everything goes: the app's spans AND Telescope's entries
  destinations: {
    collector: destinations.otlp({ endpoint: 'http://localhost:4318' }),
  },
})
```

`config/telescope.ts` needs no `otel` block. Telescope picks up the running SDK by itself.

### Sending to PostHog

PostHog ingests OTLP traces and logs with your project token. Keep a local collector as the
fallback, so development without the token still exports somewhere:

```ts title="config/otel.ts"
import { defineConfig, destinations } from '@adonisjs/otel'
import { telescopeSpanProcessor } from '@adonis-agora/telescope/otel'
import env from '#start/env'

const posthogToken = env.get('POSTHOG_API_KEY')

export default defineConfig({
  serviceName: 'my-app',
  spanProcessors: [telescopeSpanProcessor()],
  destinations: posthogToken
    ? {
        posthog: destinations.otlp({
          endpoint: 'https://us.i.posthog.com/i',
          signals: ['traces', 'logs'],
          headers: { Authorization: `Bearer ${posthogToken}` },
        }),
      }
    : { collector: destinations.otlp({ endpoint: 'http://localhost:4318' }) },
})
```

With `spanProcessors` set, the `OTEL_EXPORTER_OTLP_*` variables alone do not add an exporter:
declare every destination in `destinations`.

`signals` leaves out `metrics`: PostHog does not ingest OTLP metrics. Send them to another
destination if you want [AI metrics](/docs/telescope/packages/ai-metrics) in Grafana.

### Web and worker as separate services

`node ace add @adonisjs/otel` loads `otel.ts` from `bin/server.ts` only. A queue worker started
through `bin/console.ts` (`node ace queue:work`, a durable worker) needs the same first import,
otherwise OpenTelemetry never starts in that process:

```ts title="bin/console.ts"
import '../otel.js'
import 'reflect-metadata'
// ...
```

Then give the worker its own `service.name` so you can filter the two apart:

```ts title="config/otel.ts"
const isQueueWorker = process.env.PROCESS_ROLE === 'worker'

export default defineConfig({
  serviceName: isQueueWorker ? 'my-app-queues' : 'my-app',
  // ...
})
```

`config/otel.ts` is loaded before the app boots, so read the role from an environment variable
or `process.argv`, not from the container.

## What you see in Telescope

Open a trace in the dashboard. Next to Telescope's own entries (the request, its queries, the
exception), the waterfall shows the spans OpenTelemetry recorded during that request as **OTel
span** entries: an outgoing `http` call made with axios, a `fetch`, a method you decorated with
`@span()`, a `pg` query run outside Lucid.

`@adonisjs/otel` turns some instrumentations off by default (`pg`, `mysql`, `mysql2`, `dns`,
`net`, `socket.io`), and its events and container instrumentations are opt-in. Turn on the ones
you want in `config/otel.ts`:

```ts title="config/otel.ts"
import { EventsInstrumentation } from '@adonisjs/otel/instrumentations/events'

export default defineConfig({
  instrumentations: {
    '@opentelemetry/instrumentation-pg': { enabled: true },
    '@opentelemetry/instrumentation-dns': { enabled: true },
    '@adonisjs/instrumentation-events': new EventsInstrumentation(),
  },
  // ...
})
```

Telescope and OpenTelemetry already record some of the same things. For those, Telescope keeps
its own entry, which has more detail, and skips the OpenTelemetry span:

| Telescope watcher | OpenTelemetry span skipped | What the Telescope entry adds |
| --- | --- | --- |
| `request` | the HTTP server span | headers, bodies, user, route |
| `query` | every knex span, and the driver span under it | bindings, N+1 detection, slow-query ranking |
| `redis` | every ioredis span | the command, in the redis panel |
| `http-client` | the undici span of each call made through `instrumentFetch` | request and response, in the HTTP client panel |
| `events` | the `@adonisjs/otel` events span (`event.dispatch …`) | the event payload, in the events panel |

The `query` and `redis` rows skip by instrumentation, not per operation. A query on a connection
listed in `ignoreConnections`, a knex query that does not go through Lucid, or a redis command
the redis watcher ignores (`ignoreCommands`, `ignoreKeys`, a `sampleRate` below 1) is then in
neither place. Turn the watcher off if you rely on those filters and want the OpenTelemetry span
instead. A `fetch` you did not wrap with `instrumentFetch` always comes through as an OTel span.

When one of those watchers is off, its OpenTelemetry spans come through instead, so nothing is
missing from the trace.

Entries and spans share one trace id: an entry recorded inside an OpenTelemetry span takes that
span's trace id. A link from Telescope to your tracing backend opens the same trace.

The processor never records requests to the dashboard itself, or the work Telescope does to
store entries. Sampling, retention, the overload guard and redaction apply to these entries like
to any other.

### Processor options

```ts title="config/otel.ts"
telescopeSpanProcessor({
  // Keep a span out of Telescope
  ignore: (span) => span.name.startsWith('fs '),
  // Most spans one trace adds (default 200)
  maxSpansPerTrace: 100,
  // Attributes kept per span (default 64), and their longest string value (default 2048)
  maxAttributes: 32,
  maxAttributeLength: 1024,
})
```

## What Telescope sends to your backend

When `@adonisjs/otel` is running, each entry Telescope keeps is sent through the app's
OpenTelemetry providers, after redaction and sampling:

- an entry with a duration (a job, a scheduled task, a timed diagnostics event) becomes a
  **span**, a child of the span that was active when it was recorded;
- an entry without one (an exception, a mail, a cache hit) becomes a **log record** in the same
  trace.

Diagnostics events are named `agora.<lib>.<event>`. Other entries are named `telescope.<type>`,
with the job or task name appended (`telescope.job SendInvoice`). Every one carries
`telescope.entry_id`, so you can open the entry in the dashboard from your backend. Exceptions
also carry `exception.type`, `exception.message` and `exception.stacktrace`.

By default Telescope sends the entry types OpenTelemetry does not already trace:

```ts
['diagnostic', 'exception', 'client_exception', 'job', 'scheduled_task', 'mail', 'cache', 'profile']
```

`request`, `query`, `redis`, `http-client` and `log` are left out because `@adonisjs/otel` traces
HTTP, knex, redis, `fetch` and the logger on its own. A request entry shares the trace id of
its HTTP span, so the two are one search apart.

The [AI-usage and agent-run metrics](/docs/telescope/packages/ai-metrics) are recorded on the
app's meter, so they go wherever `config/otel.ts` sends metrics.

### Change what is sent

```ts title="config/telescope.ts"
import { defineConfig } from '@adonis-agora/telescope'

export default defineConfig({
  otel: {
    // Which entry types are sent (replaces the default list)
    entryTypes: ['diagnostic', 'exception', 'job'],
    // AI-usage metrics on the app's meter (default true)
    metrics: false,
  },
})
```

Add a type OpenTelemetry already traces only when that instrumentation is off, for example
`'query'` with `'@opentelemetry/instrumentation-knex': { enabled: false }` in `config/otel.ts`.
Otherwise the operation shows up twice in your backend.

To send nothing at all, set `otel: false`. Entries still take the OpenTelemetry trace id.

<Callout type="info">
To turn OpenTelemetry off in an environment, use `@adonisjs/otel`'s own switch:
`OTEL_SDK_DISABLED=true` set in the process environment (the shell, the container, the
deployment), or `enabled: false` in `config/otel.ts`. A value in `.env` is read too late to stop
the SDK. Telescope keeps recording locally either way.
</Callout>
